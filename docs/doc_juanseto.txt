	•	Scenario

A retail company needs a sales dashboard to help managers make strategic decisions. As the development team, your task is to work with the client to fully understand their needs.

Client Meeting Transcript – Retail Sales Dashboard Project

"So, here’s what we’re thinking… We've got all this sales data coming in every day from our stores — receipts, product sales, inventory levels — but right now, our managers have to dig through spreadsheets to see what’s going on. It’s just not efficient. We’d like something visual, maybe a dashboard, so that when a regional manager logs in, they can see right away how their stores are performing.

We want to be able to see total sales — obviously — but also, which product categories are doing well and which ones are struggling. For example, if coffee makers are suddenly not selling as much, we’d want to know ASAP so we can run a promo. It’d be great if we could filter by region or even by store. Some managers also want to see trends over time, like daily or weekly, so they can compare to last month or last year.
Another thing — our marketing team sometimes needs to see which stores are hitting their targets and which aren’t, so they can adjust campaigns. They might want to download a report. 

Oh, and some of our managers aren’t super tech-savvy, so this needs to be pretty easy to use — no complex menus.
Data-wise… well, most of it is already in our sales database, but I think some promotions data comes from another system. We’ll have to figure out how to combine those. We’d want the dashboard to be updated daily — live would be amazing, but maybe that’s too much? We’re not sure how complicated that would be. Also, mobile access would be a plus — some managers travel a lot.

I guess in short: show us the important sales numbers in a way that’s clear, let us drill down into details if needed, and make sure it works for people with different needs. But yeah, I’m sure I’m forgetting something — you’ll probably have more questions for me.”
	•	Introduction

	Understanding business requirements is the first step in any successful Data Engineering project. Before designing databases, developing ETL pipelines, or creating analytical dashboards, it is essential to identify the organization's objectives, stakeholders, and information needs. 

This report analyzes the business scenario presented for a retail analytics platform, identifying the company's main challenges, business objectives, analytical questions, functional and non-functional requirements, data requirements, user stories, key performance indicators (KPIs), and the relationship between business needs and data sources. 

The purpose of this analysis is to establish a solid foundation for the design and implementation of an ETL solution in the next stage of the project.

Question
“Do you think building a dashboard is the first step in a Data Engineering project? Explain your answer.”

R// No, building a dashboard is not the first step in a Data Engineering project. A dashboard represents the final presentation layer of a data product, but before any data can be visualized, a solid data foundation must be built.
The true first steps in a Data Engineering project involve understanding the business requirements, identifying data sources, and designing the architecture. From there, in our case, as data engineers we must build the ETL/ELT pipelines to extract, clean, transform, and model raw data into a reliable, structured format (like a data warehouse schema). However, for any other project (even if it's not data-based), the dashboard isn't the first thing.
Besides, attempting to build a dashboard first leads to the 'garbage in, garbage out' problem—visualizing incomplete, unvalidated, or unstructured data. Dashboards rely entirely on the quality, security, and performance of the underlying data infrastructure, making pipeline engineering and data modeling the actual starting point.
